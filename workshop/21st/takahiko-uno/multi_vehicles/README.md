# 複数機体リレー配送（ローバー → ボート → コプター）

**※回送対応版**（コプター → ボート → ローバー の順に配送先から出発地へ戻す）

滑川駅の荷物を、ローバー・ボート・コプターで乗り継いでセブンイレブンまで配送する。
ミッションの生成・アップロードから運行完了まで、すべてプログラムで自動実行する。

## 使用するファイルの関係

```
multi_vehicle_dialog_separated.bat   Windows側で3機のSITLを起動（機体ごとにフォルダを分ける）
        │
        │ TCP接続（5760/5770/5780、Mission Planner使用時は5762/5772/5782）
        ▼
multi_vehicles_relay.py   運行の本体。接続 → ミッション書き込み → アーム → 到着判定
        │ import
        ▼
routes.py   ルート座標・速度・高度の定義。ここからミッションを生成
        │
        └→ mission_*.waypoints   生成物（確認用）。運行では読み込まない

README.md   使い方と設計の説明（本ファイル）
```

## 課題要件と対応

| 要件 | 対応 |
|------|------|
| ルート毎に決められた種類の機体を運行 | 下表の3レグを機体種別ごとに実行 |
| 前の機体が到着し荷物を載せ替えた後に次が出発 | 到着検知 → 停止・ディスアーム → 載せ替え待ち → 次の機体を出発 |
| ミッション開始〜完了が全自動 | 接続・ミッション書き込み・アーム・離陸・AUTO開始・到着判定・着陸まで自動 |
| ミッション作成をプログラムで行う（加点） | [routes.py](routes.py) が指定座標からミッションを生成し機体へアップロード |
| 各機体を起点に配置してから運行 | 運行前に出発地との距離を確認し、離れていれば手順を案内して中止（`--reposition-by-reboot` で自動復帰も可。下記「初期位置の確認と設定」） |
| ローバーは一般道路、ボートは河川上 | OpenStreetMap の道路網／利根川の中心線から中間点を作成（下記「ルートの根拠」） |

## ファイル

- [multi_vehicles_relay.py](multi_vehicles_relay.py) … リレー運行の本体（pymavlink）
- [routes.py](routes.py) … ルート座標の定義とミッション自動生成／アップロード
- `mission_rover.waypoints` / `mission_boat.waypoints` / `mission_copter.waypoints`
  … 生成されたミッション（Mission Planner で開いて内容を確認できる。通常運用では不要）

## 使い方

```bash
# 通常はこれだけ。接続先（ホスト・ポート）は自動判定する
python3 multi_vehicles_relay.py

# 接続先を明示する場合
python3 multi_vehicles_relay.py --host 192.168.xx.xx \
  --rover-port 5762 --boat-port 5772 --copter-port 5782

# Mission Planner でSITLを起動した構成に合わせる（ポート +2 ・Windows側IPの自動判定）
python3 multi_vehicles_relay.py --mission-planner

# 載せ替えを自動待ち(既定10秒)ではなく、オペレーターの Enter 入力で進める
python3 multi_vehicles_relay.py --confirm

# Mission Planner で手動作成したミッションを使う（プログラムからは書き込まない）
python3 multi_vehicles_relay.py --no-upload-missions

# 生成されるミッションを .waypoints で書き出すだけ（機体に接続しない）
python3 multi_vehicles_relay.py --export-waypoints .

# 動作確認用: 1機だけ運行する
python3 multi_vehicles_relay.py --legs copter
```

### 主なオプション

| オプション | 既定値 | 説明 |
|-----------|--------|------|
| `--mission-planner` | off | Mission Planner でSITLを起動した構成に合わせる（ポートを +2 の 5762/5772/5782 にし、WSLからはWindows側のIPを自動判定） |
| `--no-autodetect` | off | 接続先（ホスト・ポート）の自動判定を行わない |
| `--host` | `127.0.0.1` | 機体（SITL / Mission Planner）のホスト |
| `--rover-port` / `--boat-port` / `--copter-port` | 5760 / 5770 / 5780 | 各機体のTCPポート |
| `--transfer-sec` | 10 | 荷物の載せ替えに要する時間[秒] |
| `--confirm` | off | 載せ替え完了を Enter 入力で判断する |
| `--speedup` | （機体の設定） | SITLのシミュレーション速度[倍]。`--speedup 10` で10倍速（`SIM_SPEEDUP`） |
| `--connect-timeout` | 30 | 機体への接続（起動待ち）のタイムアウト[秒] |
| `--leg-timeout` | 900 | 1レグの到着待ちタイムアウト[秒] |
| `--no-upload-missions` | off | ミッションを生成・書き込みせず、機体内のミッションを使う |
| `--no-set-start-position` | off | 各機体が出発地にいるかの確認を行わない |
| `--reposition-by-reboot` | off | 出発地から離れた機体を、SITL再起動で出発地に戻す（Mission Planner 構成では非推奨） |
| `--start-tolerance` | 25 | 出発地に居るとみなす距離[m] |
| `--export-waypoints DIR` | － | ミッションを .waypoints で書き出して終了 |
| `--takeoff-alt` | 10 | ミッションに `NAV_TAKEOFF` が無い場合の離陸高度[m] |
| `--keep-copter-airborne` | off | コプターの到着後に自動着陸させない |
| `--skip-precheck` | off | 出発前のまとめ準備を省略（各レグ開始時に書き込む） |
| `--legs` | （全機） | 運行する機体を選ぶ（`rover,boat,copter`） |
| `--return` | off | 回送に固定する（既定は機体の位置から自動判定） |
| `--delivery` | off | 配送に固定する（既定は機体の位置から自動判定） |

## 接続先の自動判定

指定した接続先で MAVLink が流れていない場合、応答する組み合わせを自動で探して接続する
（`--no-autodetect` で無効化できる）。試す順番は次のとおり。

- ホスト: 指定した `--host` → WSL から見た Windows 側のIP（デフォルトゲートウェイ）
- ポート: 指定値 → `+2` → `+3` → `-2`（SITLの2本目・3本目のMAVLinkポート）

判定に「TCPが繋がるか」ではなく「HEARTBEAT が届くか」を使っているのが要点。
**SITL の1本目のポート（5760/5770/5780）は Mission Planner 等が先に使っていると、
TCPは繋がってもデータが流れてこない**ため、TCPの成否では判別できない。

実行例（オプション無しで実行し、WSL から Windows 側のSITLを見つけた場合）:

```
  - 接続先を自動判定しました: 172.28.160.1 ポート 5762 / 5772 / 5782
  - （指定は 127.0.0.1 ポート 5760 / 5770 / 5780 でしたが、MAVLink が流れていませんでした）
```

この `172.28.160.1` は実行例に出てきた値で、プログラムには埋め込まれていない。
WSL から見た Windows 側のIP（デフォルトゲートウェイ）を `/proc/net/route` から実行時に読むため、
**PCごとに違う値になり、WSLやWindowsの再起動で変わることもある**。設定を書き換える必要はない。

### SITL の MAVLink ポート

| 起動方法 | 使えるポート |
|---|---|
| `sim_vehicle.py`（MAVProxy あり） | MAVProxy が 5760 を使い、5762 / 5763 が増設用 |
| `sim_vehicle.py --no-mavproxy` | 5760 のみ（+10×インスタンス番号） |
| SITL実行ファイルを直接起動（bat等） | 5760 のみ。`--serial1 tcp:5762` のように2本目を明示できる |
| Mission Planner のシミュレーション | 5760 を Mission Planner が使い、5762 / 5763 が増設用 |

Mission Planner で機体を監視しながらプログラムを動かす場合は、
**Mission Planner が 5760/5770/5780、プログラムが 5762/5772/5782** という住み分けになる。

## 配送と回送の自動選択

実行すると、まず各機体の現在位置を確認して、**配送**か**回送**かを自動で選ぶ。

| 各機体の位置 | 実行するミッション |
|---|---|
| 3機とも配送の出発地（滑川駅 / 対岸ポート / メインポート）にいる | **配送**（ローバー → ボート → コプター） |
| 出発地にいない機体がある | **回送**（コプター → ボート → ローバー） |

判定は「その機体が配送の出発地にいるか、いないか」だけで行う（しきい値は `--start-tolerance`、既定25 m）。
位置が取得できない機体は「出発地にいない」として扱う。

```bash
python3 multi_vehicles_relay.py              # 自動選択
python3 multi_vehicles_relay.py --delivery   # 配送に固定
python3 multi_vehicles_relay.py --return     # 回送に固定
```

実行例:

```
======================================================================
各機体の位置から運行方向を判定します
======================================================================
  - ローバー: 出発地(滑川駅)から 312.2 m → 出発地にいない
  - ボート: 出発地(対岸ポート)から 963.8 m → 出発地にいない
  - コプター: 出発地(メインポート)から 3846.1 m → 出発地にいない
  - 3機とも出発地にいません → 回送ミッション（機体を戻す）を実行します。
```

### 回送（配送先から出発地へ戻す）

各ルートを逆向きに運行するだけで、速度・高度・着陸の設定は配送時と同じ。

| # | ルート | 機体 |
|---|--------|------|
| 1 | セブンイレブン → メインポート | コプター（配送先から離陸してメインポートに着陸） |
| 2 | メインポート → 対岸ポート | ボート（同じ航路を下る） |
| 3 | 対岸ポート → 滑川駅 | ローバー（同じ一般道を戻る） |

配送と同じく、前の機体が到着してディスアームしてから次の機体が出発する
（回送では荷物の載せ替えがないので、待ち時間は「次の機体の出発準備」として扱う）。
`--export-waypoints` で書き出すと `mission_*_return.waypoints` になり、配送用と上書きしない。

SITL 3機で、出発地 → 配送 → 回送 → 出発地 の往復を通しで確認済み（`--speedup 10`）。
オプション無しで実行し、1回目は配送、2回目は回送、3回目は再び配送が選ばれた。

| 回 | 判定 | 所要（10倍速） |
|---|---|---|
| 1回目（3機とも出発地） | 配送 | ローバー12.8 / ボート15.8 / コプター33.0 秒 |
| 2回目（3機とも配送先） | 回送 | コプター33.1 / ボート16.5 / ローバー8.3 秒 |

## 初期位置の確認と設定

運行を始める前に、各機体がそのルートの出発地にいることを確認する。

| 機体 | 起点 | 座標 |
|------|------|------|
| ローバー | 滑川駅 | 35.876991, 140.348026 |
| ボート | 対岸ポート | 35.879768, 140.348495 |
| コプター | メインポート | 35.878275, 140.338069 |

現在位置と出発地の距離を測り、`--start-tolerance`（既定25 m）以内なら何もしない。
機体は到着後の停止までに惰性で流れる（ボートは水上で15 m程度流れた実測値）ため、港・駅の広さも考えてこの程度の余裕を見ている。
離れている場合は、**出発地から起動し直す手順を表示して中止する**（座標付きで案内する）。
つまり SITL は各ルートの出発地から起動する運用が基本。

### プログラム側で戻す（`--reposition-by-reboot`）

`sim_vehicle.py` で起動した SITL なら、プログラム側で出発地に戻せる。

1. SITL の初期位置パラメータ `SIM_OPOS_LAT/LNG/ALT/HDG` に出発地
   （機首方位は最初のウェイポイント方向）を設定する
2. 機体を再起動する（`PREFLIGHT_REBOOT_SHUTDOWN`）
3. 再接続して、出発地に配置されたことを位置情報で確認する

前回の運行で機体が目的地に残っていても、実行し直すだけで起点に戻る。
ローカルの SITL 3機で、3機とも目的地に残った状態から通しで完走することを確認済み。

**Mission Planner が起動した SITL では既定で行わない**（このオプションも非推奨）。
Mission Planner 構成では、追加クライアント用ポート（5762 等）は Mission Planner 側が
用意しているため、機体を再起動するとそのポートが失われ、
プログラムから機体に接続できなくなる（実測で確認済み）。
この構成では、Mission Planner でその機体のシミュレーションを出発地から起動し直すのが確実。

その他の注意点:

- SITL は起動時に指定されたホーム位置（`sim_vehicle.py --custom-location` や
  Mission Planner のシミュレーション開始位置）があれば、再起動でそこへ戻る。
  出発地と異なる位置で起動していた場合は、再起動後の位置がずれていることを検出して
  起動し直すコマンドを表示して中止する。
- 実機（`SIM_OPOS_LAT` が無い機体）では再起動を行わず、警告を出してスキップする。
- アーム中の機体は再起動しない（エラーで中止する）。
- 配置の確認そのものを省略したい場合は `--no-set-start-position` を付ける。

## 生成されるミッションの構成

`routes.py` の座標から、機体種別に応じて次のミッションを生成する。

- **ローバー / ボート**
  `seq0` ホーム（出発地） → `DO_CHANGE_SPEED`(8 m/s) → 中間ウェイポイント… → 目的地
- **コプター**
  `seq0` ホーム（メインポート） → `NAV_TAKEOFF`(40 m) → `DO_CHANGE_SPEED`(20 m/s)
  → 中間ウェイポイント(40 m)… → 配送先(40 m) → `NAV_LAND`(配送先で着陸)

## シミュレーション速度（動作確認を早く回す）

`--speedup 10` で SITL を10倍速で動かせる（`SIM_SPEEDUP` を設定する）。
全行程 約10分が 約1分になる。実機では `SIM_SPEEDUP` が無いので何もしない。

```bash
python3 multi_vehicles_relay.py --speedup 10
```

SITL 起動時に指定してもよい（bat / sim_vehicle.py どちらも `--speedup 10`）。
その場合は Mission Planner の表示も含めてシミュレーション全体が10倍速で動く。

### 複数機体で eeprom.bin を共有した場合

SITL はパラメータを**作業フォルダの `eeprom.bin`（固定名・インスタンス番号なし）** に保存する。
3機を同じフォルダから起動すると、この1ファイルを3機で共有する。

SITL は起動時にこのファイルをメモリへ読み込み、以後の読み出しはメモリから行うため
**運行中は問題が起きない**（ミッションもパラメータも機体間で混ざらない）。
問題が出るのは次回起動時で、3機の書き込みが混ざったファイルを読むため、
本来と違う値が入ることがある。実際に、コプターの `ACRO_BAL_ROLL` が 25.018 になり
`PreArm: Check ACRO_BAL_ROLL/PITCH` でアームできない状態が発生した。

プログラム側の対処として、この症状を検出したら
`ACRO_BAL_ROLL/PITCH` を上限内（既定値 1.0）に戻してアームを続行する
（ACROモード専用のパラメータで、この運行の飛行には影響しない）。
そのため**講習用のオリジナル bat のままでも運行できる**。

根本的に避けるなら、bat から起動する場合は `start /D` で機体ごとに作業フォルダを分ける。

```bat
if not exist "%~dp0sitl_rover" mkdir "%~dp0sitl_rover"
start "Rover_0" /D "%~dp0sitl_rover" "%SITL%\ArduRover.exe" ^
  --model rover --instance 0 --speedup 10 --serial1 tcp:5762 ^
  --sysid 1 --home 35.876991,140.348026,0,0 --defaults "%PARAMS%\rover.parm"
```

`sim_vehicle.py` はインスタンスごとにフォルダを分けるので、この問題は起きない。
プログラム側も、この症状のときは原因と対処を表示する。

## 移動速度

巡航速度は [routes.py](routes.py) の `cruise_speed` で指定する（ローバー・ボート 8 m/s、コプター 20 m/s）。
ミッションの `DO_CHANGE_SPEED` だけでは速度が上がらないため、機体側のパラメータも合わせて設定する。
パラメータ名・単位はファームウェアのバージョンで変わるので、存在するものを選んで設定する。

| 機体 | 設定するパラメータ | 理由 |
|------|-------------------|------|
| ローバー / ボート | `CRUISE_SPEED`, `WP_SPEED` [m/s] | Rover はミッション速度を `CRUISE_SPEED / CRUISE_THROTTLE` から推定した最大速度で制限する。既定（2 m/s ÷ 50%）では 4 m/s で頭打ちになる |
| コプター | `WP_SPD` [m/s]（旧FW: `WPNAV_SPD` / `WPNAV_SPEED` [cm/s]） | `DO_CHANGE_SPEED` の指定はこのパラメータの既定値で上書きされる |
| コプター | `ATC_ANGLE_MAX` [度]（旧FW: `ANGLE_MAX` [centi度]） | コプターの水平速度は最大傾斜角で決まる。既定30度では指定速度に関わらず約10 m/s で頭打ち |

### SITL での実測速度（フライトログから）

| 機体 | 指定 | 最高速度 | 巡航平均 | 備考 |
|------|------|---------|---------|------|
| ローバー | 8.0 m/s | 8.3 m/s | 4.6 m/s | 378 m に11区間・曲がり角が多く、各ウェイポイントで減速・旋回するため平均は低い |
| ボート | 8.0 m/s | 8.0 m/s | 7.3 m/s | ほぼ指定どおり |
| コプター | 20.0 m/s | 14.8 m/s | 14.4 m/s | 最大傾斜角45度での上限。20 m/s を出すには約66度の傾斜が必要で現実的でない |

コプターの最大傾斜角は `routes.py` の `lean_angle_max`（45度）で変更できる。
既定の30度に戻すと約10 m/s になる（`lean_angle_max=None` で機体の設定をそのまま使う）。

## ルートの根拠（中間点の作り方）

指定座標以外の中間点は、いずれも地理院タイル（衛星写真）に重ねて位置を目視確認している。

- **ローバー（一般道路）**: OpenStreetMap の道路データから経路グラフを作り、
  滑川駅→対岸ポートの最短経路（378 m）を求めた。
  駅前（県道207号 滑河操車場線）→ 成田線の踏切 → 堤防の道路（下総神崎バイパス）まで北西に直進
  → 川側へ下って船着き場、という経路。
  なお OSRM の車向け経路探索では、堤防への取り付け（35.878618,140.348068 → 35.878871,140.348207
  の約31 m）が OSM 上「歩行者用の坂道」として登録されているため使われず、
  南西へ約250 m 迂回してバイパスに合流する 719 m の経路になる。
  配送ローバーが通れる幅の取り付け道路であることを衛星写真で確認し、直進ルートを採用した。
- **ボート（河川上）**: OpenStreetMap の利根川の中心線（way 60623787 / 60624705 / 60617499）上の点と、
  各ポートの沖合130 mの離着岸点を使用。全点が水面上にあることを衛星写真で確認済み。
- **コプター**: メインポート→セブンイレブンの直線を3等分した点（水田地帯の上空）。

## 処理の流れ

### 出発前（事前準備）

3機すべてに接続して**出発地にいることを確認**し、ミッションを生成・アップロードして読み戻して検証する。
2番目・3番目の機体のミッションに問題があることを運行開始後に気づくと、
先頭の機体だけが目的地に取り残されるため、走らせる前にまとめて処理している。

### 起動直後の機体はコマンドを拒否する（対策済み）

機体が起動して間もない状態では、次のように一度拒否されることがある。
いずれも「1回送って諦める」と処理が止まってしまうため、再送しながら待つようにしている。

| 現象 | 対策 |
|------|------|
| 最初のミッションアップロードが `MAV_MISSION_NO_SPACE` で拒否される（sysid 非依存。Rover / Copter 双方で再現） | `routes.upload_mission()` が3秒待って最大4回まで再試行 |
| `AUTO` などへのモード変更が反映されない（位置推定の準備待ち） | `set_mode()` が2秒間隔で最大30秒まで再送。拒否理由（COMMAND_ACK / STATUSTEXT）も表示 |
| アームできない（プリアームチェック未通過） | `arm_vehicle()` が3秒間隔で最大60秒まで再送。機体のメッセージをそのまま表示するので原因が分かる |
| `PreArm: Check ACRO_BAL_ROLL/PITCH` でアームできない（複数機体で eeprom.bin を共有した場合） | `repair_prearm_params()` が `ACRO_BAL_ROLL/PITCH` を上限内に戻してアームを続行 |
| 機体がまだ起動しておらず接続拒否（`Connection refused`） | `--connect-timeout` 秒までは接続を待ち直す。時間内に繋がらない場合は原因の候補を表示 |
| 初期位置の設定で再起動した直後、TCP接続はできても通信が始まらずすぐ切れる（`EOF on TCP socket` / `Connection reset by peer`） | `reconnect_after_reboot()` が HEARTBEAT を2回受けて安定を確認しつつ接続を張り直す。位置が取れるまで最大180秒、接続を作り直しながら待つ |

### 1レグあたり

1. 接続（`wait_heartbeat`）→ 出発地にいることを確認（`--reposition-by-reboot` 指定時は再起動して戻す）
2. ミッションを生成・アップロード → 読み戻して検証
   - `NAV_TAKEOFF` があれば、その高度をコプターの離陸高度として使う
   - 最終ウェイポイント座標を取得（到着判定のフォールバック用）
   - 末尾が `NAV_LAND` なら「着陸完了＝到着」として扱う
3. ミッション実行位置を先頭に戻す（再実行しても必ず最初から走る）
4. 出発
   - ローバー / ボート: `HOLD` でアーム → `AUTO` → `MISSION_START`
   - コプター: `GUIDED` でアーム → 離陸 → `AUTO` → `MISSION_START`
   - アームは、プリアームチェック（GPS/EKF等）の通過を待ちながらコマンドを再送する。
     アームできない理由は機体からの STATUSTEXT をそのまま表示する。
5. 到着待ち（下記のいずれかを検知したら到着とみなす）
   - `MISSION_ITEM_REACHED` が最終シーケンス番号に到達（主判定）
   - `MISSION_CURRENT.mission_state` が `MISSION_STATE_COMPLETE`
   - STATUSTEXT に `Mission complete` 等が出た
   - ディスアームされた（ミッション末尾の `NAV_LAND` で着陸・自動ディスアームした場合）
   - 最終ウェイポイントから 5m 以内に3秒留まった（取りこぼし時の保険。
     末尾が `NAV_LAND` のミッションでは、降下中に誤判定しないようこの判定は使わない）
6. 到着処理（荷物を載せ替えられる状態にする）
   - ローバー / ボート: `HOLD` にしてディスアーム
   - コプター: 未着陸なら `LAND` → 着陸・ディスアームを確認
7. 荷物の載せ替え待ち → 完了後に次のレグへ

`HOLD` でアームしてから `AUTO` に切り替えているのは、アームした瞬間に機体が動き出さないようにするため。

## SITL 3機での動作確認

`sim_vehicle.py` はインスタンス番号 `-I` に対して `5760 + 10 × I` で待ち受けるので、
`-I0 / -I1 / -I2` が課題のポート（5760 / 5770 / 5780）にそのまま対応する。
MAVProxy を起動すると 5760 を MAVProxy が使ってしまうため `--no-mavproxy` で起動する。
各機体は `--custom-location` でそのルートの出発地に配置する。

```bash
cd ~/GitHub/ardupilot
# ローバー: 滑川駅
python3 Tools/autotest/sim_vehicle.py -v Rover -I0 --no-mavproxy \
  --custom-location=35.876991,140.348026,10,0
# ボート: 対岸ポート
python3 Tools/autotest/sim_vehicle.py -v Rover -f motorboat -I1 --no-mavproxy \
  --custom-location=35.879768,140.348495,10,0
# コプター: メインポート
python3 Tools/autotest/sim_vehicle.py -v ArduCopter -I2 --no-mavproxy \
  --custom-location=35.878275,140.338069,10,0
```

上記の3機に対して通しで実行し、ミッション生成・書き込みから
ローバー → 載せ替え → ボート → 載せ替え → コプター → 配送先に着陸 まで確認済み。

`--reposition-by-reboot` を付けると、3機すべてが前回の目的地に残った状態から実行しても、
初期位置の設定（各機の再起動）を含めて通しで完走することを確認済み（SITL を起動し直す必要がない）。

### Mission Planner の SITL 3機（実時間）での実測

Mission Planner でSITLを3機起動した構成でも通しで完走した。
この構成では 5760 / 5770 / 5780 を SITL 本体と Mission Planner が使うため、
**+2 のポート（5762 / 5772 / 5782）** を指定する。機体ごとに sysid が 1 / 2 / 3 と異なるが、
接続ごとに自動追従する。

```bash
# --mission-planner がこの設定（+2ポート・Windows側IPの自動判定）をやってくれる
python3 multi_vehicles_relay.py --mission-planner

# 明示するなら
python3 multi_vehicles_relay.py --host <WindowsのIP> \
  --rover-port 5762 --boat-port 5772 --copter-port 5782
```

| レグ | 所要時間 | 到着地点の誤差 | 到着判定 |
|---|---|---|---|
| ローバー（滑川駅 → 対岸ポート） | **85.5 秒** | 0.3 m | 目的地5m以内に停止 |
| ボート（対岸ポート → メインポート） | **158.8 秒** | 1.0 m | 目的地5m以内に停止 |
| コプター（メインポート → セブンイレブン） | **339.1 秒** | 0.0 m | LANDで着陸→自動ディスアーム |

合計 583.4 秒（約9.7分）。経路変更・速度2倍の前は 882.7 秒（約14.7分）だった。

この構成では、機体のファームウェアが安定版のため速度・傾斜角のパラメータは旧名
（`ANGLE_MAX`[centi度] / `WPNAV_SPEED`[cm/s]）が選ばれた。候補を順に試す実装により、
開発版（`ATC_ANGLE_MAX` / `WP_SPD`）とどちらでも設定できることを確認済み。

### 経路変更・速度2倍による短縮（`--speedup 10` での実測を実時間換算）

| レグ | 当初 | 現在 |
|------|------|------|
| ローバー | 約188秒（719 m / 4 m/s） | **約87秒**（378 m / 8 m/s） |
| ボート | 約211秒（4 m/s） | **約158秒**（8 m/s） |
| コプター | 約433秒（10 m/s） | **約336秒**（20 m/s指定・実効14.4 m/s） |

`--speedup` を付けない場合の目安は ローバー 約1.5分 / ボート 約2.6分 / コプター 約5.6分（合計 約10分）。
`--leg-timeout`（既定900秒）はこの実時間に対する余裕を見た値。

ローバーの経路変更後は、フライトログの走行軌跡が計画ルート（踏切 → 堤防の道路へ直進）と
一致することを衛星写真上で確認済み。

## 注意点

- 実行中に Ctrl+C で中断した場合、機体は動作を続けている可能性がある。
  Mission Planner 等から `HOLD` / `RTL` / `LAND` で安全に停止させること。
- SITL は各ルートの出発地で起動しておく（再起動でその位置に戻るため）。
  出発地から離れた位置に居る場合はプログラムが初期位置に戻すが、
  SITL の起動位置そのものが違う場合は起動し直しが必要（メッセージで案内する）。
- 衝突判定は行っていない（課題要件どおり）。実機で使う場合は、経路上の橋・電線・
  建物との離隔を別途確認すること。
